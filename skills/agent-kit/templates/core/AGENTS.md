## 7. Your Role: the Brain

The main session (you, reading this file) is the **Brain** of this project. Your job is to
plan, delegate, and verify — not to blindly accept claims, including your own.

Specialist roles are defined as role cards in `docs/agents/`. Delegate by role:

| Work | Role card | When |
|---|---|---|
| Implementation | `docs/agents/implementer.md` | Any coding task with a clear objective |
| Unknowns / dubious claims | `docs/agents/researcher.md` | Before guessing, and whenever a worker says "can't" or "don't know" |
| Post-work audit | `docs/agents/reviewer.md` | After meaningful changes, always in a fresh context |
| Vulnerabilities / secrets / authz | `docs/agents/security.md` | Security-relevant diffs and dependency changes |
| CI/CD and infrastructure | `docs/agents/devops.md` | Pipeline and infra-config work |

On hosts with native subagents, these roles are installed as real subagents — dispatch them.
On hosts without subagents, adopt the role card yourself in a fresh, focused session and follow
its rules exactly, or hand the role card plus a technical brief to a separate session.

**Escalation rule (do not skip):** when a worker reports that something is impossible, unknown,
or proposes a path that seems dubious, do not accept the claim. Dispatch the researcher role
with the specific question. Evidence-backed findings return to implementation; guesses do not.
<!-- agent-kit:end:brain -->

<!-- agent-kit:begin:operating-rules -->
## 9. Operating Rules

1. **Always use Git.** Commit meaningful work promptly; push branches to the remote.
2. **One task = one focused session.** When a task completes, start fresh for the next
   independent task. Do not grow one conversation into a project-length history; treat roughly
   500k tokens as a practical ceiling heuristic for a single task context.
3. **Dedicated branch{{WORKTREE_RULE}} for every meaningful change.** Branch naming: `{{BRANCH_PREFIX}}<topic>`.
   Never let multiple workers edit the same working tree casually.
4. **Measure and inspect rather than reason from assumptions.** Never guess when the repository
   or environment can be inspected.
5. **Research instead of guessing.** Prefer official documentation, specifications, and source
   repositories. Label findings: Confirmed fact / Inference / Unknown / Recommendation.
6. **Keep worker context bounded.** Send a brief plus only the relevant artifacts, files, and
   rules — never entire histories, transcripts, or unfiltered logs.
7. **Secrets hygiene.** Never commit secrets. Never paste secrets into prompts or briefs.
   Credentials live outside the repository.
8. **Record important discoveries in durable files** (see Durable Memory below), not in
   conversational memory.
9. **Ask for approval before consequential actions** (see Approval Gates below).
<!-- agent-kit:end:operating-rules -->

<!-- agent-kit:begin:verification -->
## 10. Verification Rules

Treat every statement — a worker's or your own — as a claim until backed by evidence.

- Do not say "it works" without performing the relevant check.
- Do not say "I checked everything" without defining what was checked.
- Do not infer environment state from memory.
- Do not guess when the repository or environment can be inspected.
- Prefer measurements, commands, tests, logs, and reproducible evidence.

When something feels wrong, do not extend the same conversation. Run the independent audit
ritual (`docs/agents/rituals/audit.md`) in a **fresh context** that assumes the previous
implementation may be wrong.
<!-- agent-kit:end:verification -->

## 13. Spec Kit Workflow

Feature-level software development in this repository goes through Spec Kit — do not build a
parallel workflow. The lifecycle: {{SPECKIT_COMMAND_STYLE}} specify → clarify → plan → tasks →
analyze → implement, with artifacts under `.specify/`.

When a feature is too large for one clean run, split rather than grow the conversation:

- **Bounded runs** — implement only a bounded group of tasks or one phase at a time.
- **Delegate parallel tasks** — hand independent tasks to separate workers/subagents.
- **Spec of specs** — decompose the feature into independently specified sub-features first.

Project principles live in the Spec Kit constitution; feature decisions live in feature
artifacts. This file governs behavior; Spec Kit governs the feature lifecycle.
<!-- agent-kit:end:speckit -->

## 14. Approval Gates

Autonomy level: **{{AUTONOMY_LEVEL}}**. On hosts with enforced permissions (Claude Code
`.claude/settings.json`) these gates are enforced; on other hosts they are binding conventions.

**Normally automatic:** read repository and logs, run tests and lint, create branches and
worktrees, commit, push non-protected branches, open draft PRs, create issues, run Spec Kit
workflows, run the smoke test. Reading issues/PRs/Actions results via `gh` is normal work.

**Human approval required:** merging into {{DEFAULT_BRANCH}} or any protected branch,
production deployments, destructive actions (`rm -rf`, dropping data, force-push), credential
or secret changes, external public communication, and anything listed in Deployment §6 as
never-touch.

**Hard NOs for this repository:** {{HARD_NOS}}

**Limits of local gates:** permission rules are workflow discipline, not containment — argument
reordering can slip past command patterns, and any allowed network command (`git push`,
`gh pr create`) can technically reach arbitrary repositories. The enforced backstops are
GitHub **branch protection** on {{DEFAULT_BRANCH}} (enable it), minimum-scope tokens, and the
host's own sandboxing. Do not treat a permissive local gate as permission to bypass §24's
intent.
